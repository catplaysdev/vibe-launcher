# Codex／Claude 切換帳號：問題與解決方案對照

更新：2026-10-12。依據：Codex CLI 0.162.1、Claude Code 2.1.296 的實測與官方文件；細節見
[Codex 驗證紀錄](codex-switch-feasibility.md)、[Claude 設計](claude-switch-design.md)、[CLIProxyAPI 研究](cliproxyapi-reference.md)。

狀態欄：**已實作**＝程式已完成且有測試；**已實測**＝真實帳號驗證過；**未驗證**＝尚無實證。

## 1. 基本差異

| 項目 | Codex | Claude Code |
| --- | --- | --- |
| 官方可用的接管方式 | `codex --remote` 讓 TUI 連到 Launcher 的 bridge，背後是官方 `app-server --stdio` | 沒有前後端分離；只能在同一終端結束後以 `claude --resume <id>` 重開 |
| 切換時畫面 | 不中斷，TUI 持續連線 | 會重繪一次，對話保留 |
| 確切對話識別 | thread id（bridge 從 `thread/start` 回覆取得） | `--session-id <uuid>` 由 Launcher 指定，紀錄檔名即此 id |
| 結構化事件來源 | app-server JSON-RPC 通知 | 以 `--settings` 只為該次啟動注入 hooks（不改使用者設定檔） |
| 為何不用 proxy（CLIProxyAPI 模式） | 需代管 OAuth、偽裝官方客戶端、代理 API，違反專案邊界 | 同左 |

## 2. 對話與安全時點

| 問題 | Codex 解決方案 | 狀態 | Claude 解決方案 | 狀態 |
| --- | --- | --- | --- | --- |
| 不能用「最近一次對話」猜測 | 交接與重開都用確切 thread id | 已實作、已實測 | `--session-id` 指定、`--resume <id>` 接回；還原時取該專案最新紀錄的確切 id | 已實作、已實測 |
| 何時可以切換 | 回合結束、無工具、無核准、無子代理、無背景請求 | 已實作、已實測 | 提示數＝結束數、`PreToolUse` 皆有對應結果、無子代理、無背景工作；開始工作的事件以同步 hook（`onFailure: "block"`）先記錄，交接時取得交接鎖後重讀，之後的 prompt／工具被擋下 | 已實作（自動測試）；真實 CLI 尚未實測 |
| 工具結果不明 | 停下提示，絕不重播 | 已實作 | 同左（以 hook 事件判斷）；略過權限檢查的工作階段一律手動 | 已實作 |
| 兩個程序同時寫同一對話 | 原 app-server 結束後才啟動新的；重開時等待舊程序最多 20 秒 | 已實作、已實測 | 先結束 Claude、複製紀錄，再以新帳號 `--resume`；新 CLI 回報同一對話後才提交新帳號，失敗、逾時或模型不符時以原帳號重開，回報帳號與實際程序一致 | 已實作（自動測試） |
| TUI 自己的輔助對話（產生標題） | 只接受「ephemeral、唯讀、無任何工具」形態，用工具即停下 | 已實作、已實測 | 不適用 | — |
| 原生訊息過大 | `plugin/list` 單行 13.2 MB；上限 64 MiB、分段送出 | 已實作、已實測 | 不適用 | — |

## 3. 環境層（同一台機器所有帳號共用）

| 問題 | Codex 解決方案 | 狀態 | Claude 解決方案 | 狀態 |
| --- | --- | --- | --- | --- |
| 每帳號一份家目錄造成分岔 | 啟動時從原生 `~/.codex` 同步；比對改看實際載入內容 | 已實作、已實測 | 同步 skills、agents、commands、hooks、設定與 `CLAUDE.md`；外掛以 `--plugin-dir` 由原生目錄載入；交接前比對 | 已實作、已實測 |
| 指示檔、設定擴充 | 內容指紋比對，不同即阻擋 | 已實作 | 同左；交接時以旗標指定的模型與推理強度不比對預設值 | 已實作、已實測 |
| skills | 官方 `skills/list` 比對非外掛 skills 與 SKILL.md 內容 | 已實作、已實測 | 共用資料夾內容比對 | 已實作 |
| 「一律允許」核准規則 | 唯讀比對 `rules/*.rules`，不合併；不同時由使用者取消或明確「以目前規則對齊目標帳號」（先備份，目標帳號在其他終端使用中則阻擋） | 已實作（自動測試） | `permissions` 屬共用設定，啟動時同步 | 已實作（同步） |
| 用連結共用資料夾 | 不採用（曾導致終端無法開啟，且違反路徑安全檢查） | — | 同左 | — |

## 6. 額度

| 問題 | Codex 解決方案 | 狀態 | Claude 解決方案 | 狀態 |
| --- | --- | --- | --- | --- |
| 額度資料來源 | 官方 `account/rateLimits/read`（可主動查詢）＋回合中的 `account/rateLimits/updated` | 已實作、已實測 | 狀態列輸入的 `rate_limits.five_hour／seven_day` 寫入共用快取；只能被動取得；使用者自訂的狀態列由 Launcher 包一層後照常執行 | 已實作、已實測 |
| 局部更新、舊資料 | 每個額度視窗各自記錄觀察時間，舊事件不視為新資料 | 已實作 | 最後觀察值一小時內有效，且任一視窗重設後即失效 | 已實作 |
| 偵測「因額度停下」 | 回合錯誤 `usageLimitExceeded`；此時對話狀態為 `systemError` 仍視為檢查點 | 已實作、已實測 | `StopFailure` hook 的 `error: rate_limit` | 已實作；以本機假服務實際觸發確認 |
| 切換後自動接續 | 注入一次「從檢查點繼續、不重做工具」；交接後 120 秒內重試 | 已實作、已實測（模擬額度＋真實帳號） | 以 `claude --resume <id> "<繼續提示>"` 重開 | 已實作、已實測（模擬額度＋真實帳號） |
| 全部不足時 | 可信重設時間到、重設後重新查詢、安全時點才自動接續；只通知不自動開始；重設瞬間的舊觀察不會抹掉可信重設時間 | 已實作、已實測（模擬額度＋真實帳號） | 同一規則，`resets_at` 為可信時間 | 已實作、已實測（模擬額度＋真實帳號） |
| 不知道額度的帳號 | 不作為切換觸發，也不被自動選中 | 已實作 | 近一小時沒有觀察到的帳號額度未知，自動流程不選它，手動可切 | 已實作 |

## 8. 遠端（SSH）與執行環境

| 問題 | 解決方案 | 狀態 |
| --- | --- | --- |
| 遠端 helper 超過 Windows 命令列 28000 字元 | 依動作只傳需要的程式；過長時改以每字元 14 bits 的緊湊編碼另外帶入 | 已實作；真實主機未驗證 |
| 關閉終端是否停止監測 | 本機終端結束整個程序樹；SSH 分離後 tmux 仍在則監測持續，重新接回恢復輪詢 | 已實作；SSH 未驗證 |
| 舊版 CLI | 不支援 `--remote` 時照常以一般模式啟動並提示 | 已實作 |
| Claude 子資料夾匯入上層 `CLAUDE.md` | 會跳出「外部匯入」確認；受管理啟動不代替使用者回答 | 已知限制 |

## 9. 尚未驗證

- Codex：真實額度用完、重設後自動接續；SSH／tmux 主機；Windows 安裝檔。
- Claude：SSH 主機上的 hooks（以遠端 `runtime.py --claude-hook` 執行）；真實伺服器回應 429 時的行為只以本機假服務確認。

## 10. 測試工具與已確認項目（2026-10-12）

| 項目 | 方法 | 結果 |
| --- | --- | --- |
| 額度失敗 → 切換 → 自動接續、全部不足 → 等可信重設 → 同帳號接續、低額度 → 自動切換 | `scripts/simulate_quota.py` 的模擬額度（最多 1 小時、狀態標示「模擬額度」）＋真實帳號（Codex gpt-6-luna／low、Claude haiku） | Codex、Claude 各情境通過；過程中修正兩個真實 bug：重設瞬間抹掉可信重設時間；交接後仍以來源帳號的指示檔路徑為比對基準 |
| Claude `StopFailure` 事件格式 | 暫時 profile＋假 API key＋本機 429 服務（不耗額度、不碰真實憑證） | `error: "rate_limit"` |
| 使用者 hooks 與注入 hooks | 同上 | 兩者皆執行（合併） |
| 使用者自訂狀態列 | 同上 | 包一層後照常顯示，額度仍記錄 |
| SSH | 由使用者在 Launcher 操作，`scripts/check_remote_switch.py` 唯讀檢查 | 待使用者執行 |
